# Simplified Student Import

In a program's Students tab, open the existing **Import Students** modal. Upload a supported file, map roster fields, review the proposed results, then confirm. The modal keeps the existing styling and upload → map → review → results flow.

The normal UI no longer maps **Subject Codes** or **Subject Block**, and no longer offers **Also add subjects to existing students**. Its requests carry `mode: regular` and do not send an enrollment-update flag or subject mappings. Regular **Year Level** and **Block** mappings remain available. These describe the student's home class, not the block attended for a particular subject.

Use [students.csv](import-templates/students.csv) as an example. Map Student ID, Email, First Name, Last Name, Year Level and Block. Middle Name and Suffix remain optional. Student ID remains the only required column mapping so an existing-student ID-only file can still be reviewed/skipped; each *new* regular student requires a valid email, first/last name, year 1–6 and block up to 10 characters. The current program supplies the academic program. Existing class sections are reused; if absent, a year/block section is created as in the previous importer. Teaching assignments are not invented. The student's evaluation eligibility still comes from that section's offerings in the active review period.

**Irregular? (Y/N)** remains an optional detection mapping: blank/N/no/false/0 means regular; Y/yes/true/1 identifies irregular. Other values are errors for new rows. As in the existing column-mapping workflow, unmapped columns are ignored: map Irregular? when a file contains mixed statuses; omitting that mapping declares a regular roster. It does not authorize bulk irregular enrollment in this simplified workflow. New irregular rows receive an error directing the administrator to **Add Student → Irregular → select attended courses and blocks**. No account, arbitrary enrollment or partial eligibility is created for those rows. Existing irregular students are skipped by the roster import, preserving current and historical enrollments.

Already existing students are never updated or enrolled by this mode. Existing program/email mismatch safeguards still report errors rather than changing the record. Repeated identical students are grouped using the existing importer; conflicting repeated rows are errors. Reimporting completed regular rows skips their existing records, preserving names, identifiers, passwords, section, timestamps, enrollments and evaluations. Review writes no academic records. As before, valid independent rows may import while invalid rows fail; account/student/section creation is transactional per student. Existing account email delivery behavior is retained (local previews use log-only mail).

Simplified upload tokens are tied to the uploader and program. They cannot be used with legacy Student Import mode; a token created without simplified mode cannot be switched into simplified mode. The server rejects subject mappings and an enabled update-existing flag in simplified requests, independently of frontend filtering. Imported jobs reanalyze rows with the same mode, so reviewing a regular roster does not later enable irregular enrollment.

## Legacy compatibility and limitation

The normal interface no longer exposes bulk irregular-subject import or adding subjects to existing irregular students. Administrators must use the supported manual workflow there. This is an intentional limitation of the client-requested simplification, not a replacement enrollment model.

Existing authorized legacy API integrations that **omit `mode`** retain the prior subject-code/block mappings and explicit `updateExisting: true` workflow. Their existing safeguards and limitations remain; this task does not redesign that API, grant new privileges, or make its enrollment updates the default. Use these only as an explicit authorized workflow, never by treating a simplified roster upload as a legacy enrollment request. Historical enrollments are not migrated or cleared. Without an active review period, the simplified regular roster can still create/skip regular records; irregular enrollment continues to require the existing active-period/manual rules.

The original Laravel/PHP, React JSX/Inertia, MySQL schema, Tailwind styles, installed spreadsheet library and import controller/analyzer/job are preserved. No dependency, migration, authentication or evaluation-rule change is introduced.
