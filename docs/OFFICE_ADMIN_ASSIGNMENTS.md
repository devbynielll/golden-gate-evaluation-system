# One Office Admin per office

Super Admin uses the existing Admin Accounts Add/Edit modal to select an Assigned Office for Office Admin accounts. Several offices may have separate accounts; the same office cannot be assigned twice. This is a maximum, not automatic provisioning. Department Admin remains a single account under existing validation. Roles remain immutable after creation. Office assignment does not reset credentials, alter identifiers, create evaluations or transfer historical answers.

## Legacy transition and safe deployment

The additive migration `2026_10_31_000001_add_office_assignment_to_users.php` adds nullable users.office_id, a foreign key and the named unique index users_office_assignment_unique. It does not update/delete any existing account, reset credentials, infer ownership or map offices automatically. Existing Office Admin accounts remain NULL/unassigned. The original historical scope-removal migration is NOT a deployment/rollback tool; never rerun it on populated client data.

Before any real deployment: obtain the client's verified database backup and authorized deployment window; verify schema/migration state on an isolated restored copy; test the additive migration and constraints against the actual MySQL version; explicitly identify which office the legacy account represents with the authorized owner. No client-specific mapping is embedded in source. Deploy matching schema and application code together. Until Super Admin edits the legacy account and selects its confirmed office, dashboard/reports return403 and no office data is disclosed. The account remains visible as Unassigned — office access blocked. The Super Admin must map it through Edit Account with its current name/email/ID, without password reset. Plan this access interruption before cutover. Existing sessions resolve fresh ownership on every request.

New Office Admin creation requires a valid unassigned office; edit likewise requires an explicit valid assignment. Reassignment frees the old office and changes access on the next request, preserving the account identity/password and every evaluation tied to the office. Duplicate claims fail validation; the database unique constraint remains authoritative when requests race after validation, and constraint failures roll back with a validation message. Original email-delivery rollback remains: failed credential email leaves no new account/office claim. Office deletion sets office_id NULL, retaining the admin account and failing closed thereafter; existing evaluation deletion semantics of Office administration are not redesigned here.

Migration down removes only the new ownership schema, so it loses ownership mappings. Never roll back to old global-access application code as a casual recovery step; it could expose all-office data. Preserve mappings and use a separately approved rollback/maintenance plan. No existing/client database migration was run in this task.

## Scope, dashboards, reports and exports

Assigned Office Admin sees only their office's current-period dashboard: office name, stored ratings, submitted response count, feedback, eligible-student expected/pending counts and completion. Eligibility follows existing Student office rules: department-specific offices apply to students whose program belongs to that department; a global office (department_id NULL) applies to all students. Responses/ratings preserve stored evaluation semantics; completed eligible students determine progress. Without an active period, dashboard ratings/responses/expected/pending/progress are empty/zero, while historical reports remain available for the assigned office.

Office Reports always apply the server-resolved assigned office, including search, page, period and Inertia partial requests. A conflicting explicit office_id is forbidden; arbitrary ignored parameters cannot widen the underlying office filter. Office Admin does not receive other offices' names, ratings, feedback, totals, department filter lists or export rows. Current report PDF exports are generated by the existing browser utility from those already-scoped report props; there is no separate unscoped export endpoint. Both summary and individual PDF actions use the same scoped rows. Saved/downloaded reports from past authorized access cannot be revoked by later reassignment; new requests resolve the new office scope.

Report/dashboard cache keys include office identity separately from Super Admin aggregate reports. Ownership is freshly resolved before cache access; null/missing assignments fail before any report data is read. Assignment changes flush caches. Super Admin retains all-office dashboard/report oversight and account management; Department Admin, Student and Criteria permissions are unchanged. Office Admin still has no Office Criteria access; shared versus office-specific questions remain a separate client decision. No criteria, question, answer or student evaluation schema/policy is changed.

It does NOT establish real concurrent MySQL transaction/lock behavior. The unique index is the database-level safeguard; parallel MySQL creation/update testing and production integration remain pending and must be completed on a separately authorized isolated MySQL target. No existing MAMP or client database was accessed, and no concurrency certification is claimed.
